## What was built

| Path | What |
|---|---|
| `plugin/desktop/plugin.js` | The pane. One plain-ESM file, no JSX, imports only `@hermes/plugin-sdk` and `react`. Registers one `panes` contribution (`placement: 'right'`, `width: '380px'`, title "Calls"). |
| `tools/pane-preview/` | Offline harness: renders the real `plugin.js` against fixture snapshots, in a 1440 px window, light and dark. `README.md` says what is real and what is faked. |
| `tools/pane-preview/fixtures/` | One `GET /calls` snapshot per state, contract-shaped, all labelled sample (Sample Airline / Bistro / Clinic / Pharmacy, `+1 555-01••`, codes as `[CODE]`). L1 can reuse them. |
| `tests/l3/` | 46 offline tests (`node --test tests/l3/pane.test.mjs`). |

The pane shows:
- the live call list, shown only when there is more than one call, with the most urgent call first;
- the selected call's state: a large tabular clock for the time in the current state, plus "N into the call" once a person is on the line, so the hold time stays visible;
- the masked transcript (`[CODE]` renders as a "code hidden" chip; new lines rise in; auto-follow only while you are at the bottom);
- Take over, Say this (inline composer) and Hang up (the app's `ConfirmDialog`, which names the cost: "You will lose your place in the queue after 38 minutes on hold");
- the call summary, a failure reason with a next step, and the empty, loading, error, stale and 409-conflict states.

It owns no telephony:
- Every control is a POST to the L1 backend carrying `{idempotency_key, revision}`.
- Nothing is shown optimistically: "Asked Hermes to bring you in" stays until the backend state moves.
- Closing the pane touches no call.
- Updates come from the `plugin.hermes-line.call.updated` event, plus a `ctx.setInterval` poll (5 s while a call is live, 30 s idle).
- A native OS notification fires once per call when a person answers. This happens only on an observed transition, never on first load.
- On a profile switch the pane drops the old profile's calls and fetches again.

## Questions for the coordinator (contract; not owner decisions)

1. **No `state_since` on Call.** The hold timer has to know when the current state began. Today the pane takes the timestamp of the newest `system` transcript line, which assumes L1 writes one system line per state transition, and falls back to `started_at`. It already prefers a `state_since` field when present.
   - Options: A) add `state_since` (ISO 8601) to Call; B) keep the system-line convention and write it into the contract.
   - Recommend A: one explicit field cannot drift with transcript wording.
2. **Meaning of `mode`.** The pane reads it as the owner's chosen plan (`owner` = bridge me in, `agent` = Hermes finishes the call). That reading drives the copy and whether Take over is the primary button.
   - Options: A) plan, as implemented; B) who is speaking right now.
   - Recommend A: the state already says who is speaking.
3. **Revision scope.** POSTs send the snapshot-level `revision` from `GET /calls`, and an event re-fetches when its `revision` differs.
   - Options: A) snapshot-level revision, as implemented; B) per-call revision.
   - Recommend A: it is what the contract's GET returns.
4. **`ts` format.** The contract does not say. The pane accepts ISO 8601 strings or epoch seconds/milliseconds. Recommend writing ISO 8601 into the contract.
5. **Mask token format.** The pane renders any `[UPPERCASE]` token (S3's `[CODE]`) as a "code hidden" chip and never shows the raw token. If L1 or L4 masks another way (for example bullets), tell L3.
6. **Package id.** The plugin id is `hermes-line`. It must match the L1 package and catalog name, because the namespace `/api/plugins/hermes-line` and the event prefix depend on it.

No owner decision is needed for this version.

## Honest critique of the render

**What works:**
- The 40-minute hold reads calm: one big tabular clock, one sentence, nothing moving except the seconds.
- "A person answered" is now the loudest frame: accent label, tinted stage, total call time kept.
- The app's own components make it look native in both themes.

**What is still weak:**
- The layout (header, status block, buttons, log) is category-standard. It is clean, but nothing about it is unmistakably *phone*. A demo viewer will remember the clock, not the pane.
- During a long hold the transcript takes most of the height while nothing new is said. A collapsed "nothing new since 9:24" state would be calmer.
- In a compressed 90-second video at 380 px, the 11-13 px transcript text will be hard to read. Record zoomed in, or widen the pane for the demo.
- The ringing state is now static. That is calmer, but it gives no sense of "ringing right now" beyond the ticking clock.
- No keyboard shortcuts, so the fastest path when a person answers is still a mouse click.
- When a transcript is scrolled, the first line slides under the "Transcript" heading with a hard edge (visible in the `ringing_owner` capture). A top fade would read better.
- Not yet seen inside a running Hermes Desktop, so the exact pane chrome, tab strip and resize behaviour are unverified.

## Critique of each direction

**A Quiet:**
- **Works:** honest, native and finished. Every coordinator issue is fixed, it would pass any review, and it costs nothing to maintain.
- **Weak:** it is still a status card over a log. "A person answered" is a blue headline on a 8 % tint, and nobody watching a 90-second demo will remember it.

**B Story:**
- **Works:** the most *useful* of the three for a long call. You see at a glance that the menu took 0:41, the hold 38:32, and that you are now in the person phase. Old chatter folds away, so a 40-minute hold doesn't bury the live part, and the ended view reads like a receipt of the call.
- **Weak:** the person-answered moment is only a blue node and heading, not much louder than A. The rail and collapsed rows make the pane busier. With a short call (no hold) it looks thin.
- **Hidden cost:** it leans hardest on the contract assumption that the engine writes a system line at each phase boundary.

**C Signal:**
- **Works:** it gives the demo its one memorable frame. The pane is quiet grey with "On hold for 38:12" and "Last heard at 9:24 AM: …", then the whole top floods blue with "Someone picked up." and the business's actual words. When it ends, the headline *is* the result ("Moved the flight to Friday, 9:40 a.m. departure.") with the time strip as a receipt. It uses only app tokens and native buttons and reads well at 380 px in both themes.
- **Risks:**
  - The big colour field is loud: for a surface Can looks at daily it must stay reserved for the moments that need him, which is how it is built.
  - The newest-first transcript breaks chat convention (I chose it so the newest line is always where the eye lands).
  - The quote repeats in the transcript below.

**What I would ship: C**, with two borrowings from B: fold transcript lines older than the current phase, and keep B's phase names in the strip legend. A remains the safe fallback.

## How Desktop loads a plugin (from the SDK docs and the installed v0.22.5 source)

- The desktop half of a unified package (`plugins/<id>/desktop/plugin.js`) is copied by Electron into the **app-level** root `<HERMES_HOME>/desktop-plugins/<id>/`, with a `.hermes-package.json` marker.
  - It is one root for every profile (`apps/desktop/src/contrib/runtime-loader.ts`).
  - It is **opt-in**: it stays off until enabled in Capabilities → Plugins, a renderer decision stored in `localStorage` key `hermes.desktop.pluginDecisions.v2`.
- The REST half (`dashboard/plugin_api.py`) is mounted by the gateway only when the plugin is in that home's `config.yaml` `plugins.enabled` (`hermes_cli/web_server_dashboard.py::_plugin_api_mount_skip_reason`). `requires_env` does not gate the mount.
- Hermes Line's call service starts only when the plugin's own config sets `enabled: true` (`hermes_glue.register`). Left unset, enabling the plugin starts nothing telephony-related.
- Desktop supports a fully isolated second instance; its own e2e suite uses it (`apps/desktop/e2e/fixtures.ts`):
  - `HERMES_HOME` + `HERMES_DESKTOP_USER_DATA_DIR` + `HOME` all point at a sandbox;
  - `HERMES_DESKTOP_IGNORE_EXISTING=1` and `HERMES_DESKTOP_ISOLATED_BACKEND=1`;
  - a unique `HERMES_DESKTOP_APP_NAME`, so the single-instance lock never collides with the owner's app;
  - the dev Electron runs the built `dist/` against the checkout backend.
