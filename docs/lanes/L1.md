### State-machine paths covered by `tests/l1/test_flows.py`

Outbound dial with the disclosure greeting (and disclosure off); IVR via DTMF (one press per prompt, validated,
model text suppressed after a key press) and speech; silent hold with repeated messages (no Hermes turns, no model
calls); live-person confirmation question then human detected; owner mode: ring owner (Twilio number as caller ID),
private whisper, press 1, Relay `end` with handoff, business moved into a conference, owner hang-up ends all;
owner declines / no answer → agent fallback or polite end; take over from the pane while on hold (owner misses it →
back on hold); agent-completes mode with the finish tool; callbacks matched to one open task by number (owner rung
with the callback grant), unmatched or ambiguous → take a message, busy line or wrong number → `<Reject>`; summary
posted through the outbox to the originating chat; voicemail (hang up, or leave a message when allowed); no answer;
busy; provider failure; business hang-up during hold and during talk; business hang-up while the owner rings
(owner leg cancelled); dropped relay (grace period, then hang up), reconnect via the Connect action then give-up;
max-duration watchdog; barge-in and talk-over; owner "Say this"; agent/model unavailable (apology, end); bounded inbox.

### Consent and gates

Every leg (business dial, owner ring, take-over, callback ring) goes `check_destination` (L2) → quiet hours (business
legs; callbacks never ring the owner in quiet hours) → single-use L2 consent bound to `{destination, role, call|callback,
line}` → an unforgeable single-use `DialPermit` → `TelephonyAdapter.place_call`. The destination gate also runs when the
request is made (before approval is shown). `approve` issues the dial grant (300 s) and owner-bridge grants. L2 caps a
grant at 3600 s, so `GrantBook` renews bridge grants by consuming and re-issuing the identical binding (lifetime
bounded by `max_call_minutes`); a used or lost grant is never revived. An explicit owner take-over (pane/slash) is
fresh consent; a tool take-over can only use the remaining grant. One call per line (async line lock + live-call
check). `tests/l1/test_gates.py` asserts zero adapter calls for 28 bad destination shapes, model/tool approval,
dial-time re-check, quiet hours, forged/reused permits, reused/mismatched consent, hard denies with a valid token,
an owner number off the allowlist, a spent bridge grant, and quiet-hours callbacks.

## 7. Round 2 (coordinator brief `docs/briefs/L1-round2.md`)

### 7.1 Public driver: ACP

The documented public way for a plugin to run a streamed, tool-using turn on the user's own Hermes is **ACP**:
the `hermes acp` CLI speaks the Agent Client Protocol (JSON-RPC over stdio; docs `programmatic-integration.md`,
`acp-internals.md`). In v0.22.5 it is a viewer: the profile's gateway owns the session (`acp_adapter/
gateway_server.py`, `hermes_cli/gateway_client.connect_gateway`, which starts an idle-exit gateway when none runs).
The TUI-gateway JSON-RPC has no documented launch command for plugins, and the API server needs the user to
enable a platform and a key, so neither is the better fit. `plugin/line/engine/acp_driver.py` implements the same
driver interface over it (no Hermes import):
- streaming `agent_message_chunk` text only (thoughts and tool updates never reach the caller);
- barge-in = `session/cancel`; the gateway history cannot be rewritten, so the next prompt starts with what the
  caller actually heard;
- the briefing is sent with the first prompt (ACP has no system-prompt field); `ask` uses a second session;
- every permission request is declined; fs/terminal client capabilities are off;
- the gateway session id is registered so in-call tools find their call; when the tool runs in another process of
  the profile it goes through the store as a `call-agent` command that can only press digits, finish or ring the
  owner for the call that session drives (tested, including forged approve/hang-up attempts);
- only masked caller speech is sent to either driver (an ACP session is persisted by Hermes).

`driver: auto|embedded|acp` (default `auto` = embedded when `line/engine/embedded.py` ships, else ACP). The embedded
factory, the only private imports, now lives alone in `embedded.py`; deleting that one file produces the ACP-only
package that validates without the private-import warning.

|---|---|---|
| Per-install path secret `/t/<secret>/twilio/...` | yes | yes. 256 bits, `secrets.token_urlsafe`, file `plugin-data/hermes-line/ingress-path.secret` (0600), constant-time compare, wrong/missing → bare 404 |

| `X-Twilio-Signature` | required on every webhook and WS upgrade | not available |
| One-time stream tokens | single-use, 120 s, bound to call and kind | same |
| CallSid correlation per leg | yes | yes |
| REST check (API key) | not needed | before a leg's first side effect: the SID exists on this account, direction and from/to match the task (outbound: to = destination, from = caller ID; inbound: to = line number, from = caller; owner leg: to = owner, from = line). | Terminal / conference-end events | trusted (signed) | re-confirmed against REST; unconfirmed → ignored and logged |
| Owner "press 1" | trusted (signed) | refused unless REST shows the owner leg answered (`in-progress`) |
| Failures | 403, logged | 404/403/`<Hangup>`/`<Reject>`, logged masked (`ingress_rejected`: reason, route, masked SID; never the secret) |

`tests/l1/test_ingress_fallback.py` (16 tests): a full call without any signature; wrong/missing/oversized path
secret on HTTP and WS; one-time relay token reuse; answer rejected for an unknown SID, another account, other
numbers, wrong direction, and Twilio unreachable (fails closed); five forged terminal statuses; four inbound
rejection shapes; forged owner accept before the owner answers; an owner leg whose REST record has another number;
forged conference-end during a live bridge; signature mode still refusing unsigned requests. Each asserts zero side
effects (no provider call, call record, relay token or session) and a masked log entry.

**What the fallback does not protect against, compared with signatures** (updated in round 4 with the R1 review's
additions; items marked *fixed* describe what remains after the round-4 fix):
- **Anyone who learns the path secret** can send webhooks. The secret lives in URLs, so it appears in Twilio's call
  and debugger logs, in the tunnel provider's and any proxy's logs, and wherever a TwiML document or URL is copied.
  Signatures need the Auth Token, which never travels. Everything below assumes the secret is exposed.
- **Forged events about a real, verified call** that REST cannot contradict at that moment are accepted: non-terminal
  status updates, and the owner's key press once the owner leg is answered (REST shows the leg is up, not which key
  was pressed). REST shows a leg's existence, numbers and status, not the authenticity of an event or the physical
  identity of whoever is speaking.
- **Fresh relay tokens to the requester.** Per-call one-time tokens are no remedy when an accepted HTTP request hands
  the requester new ones: the TwiML goes to whoever sent the request. *Fixed in part (M2):* each relay generation has
  exactly one token set; `/answer` retransmissions return that generation's TwiML (spent token) and mint nothing; a
  Connect completion is processed once per generation (single-flight since the R1 delta: overlapping requests share
  one completion and one answer), is not believed while that generation's socket is still connected, and only a
  genuine new recovery issues the next generation. Remaining: the first completion of a
  generation whose socket really dropped can be raced by a forger, who then receives that recovery's token and can
  attach first as the "caller" (one socket per call; the real relay is then refused).
- **The relay `setup` frame is not a credential:** it carries the CallSid, which the attacker already needs and
  knows. Frames sent before `setup` are now ignored (round 4), so ordering is enforced, not authenticity.
- **Historical inbound admission and cached caller substitution.** *Fixed (H2):* the REST cache is keyed by account
  plus the full expectation (direction, To, From), a conflicting expectation for a cached SID is rejected without a
  lookup, entries expire (4 h) and are bounded (256, oldest evicted) and are dropped when the call ends, the
  provider-returned SID must match, inbound admission requires a live provider status (queued/ringing/in-progress),
  and every inbound CallSid is admitted at most once, persistently: a Twilio retry of a live admission gets the same
  TwiML (no new session, token or grant); a replay after the call ended or after a restart is refused. Remaining: a
  forger who wins the race against Twilio's own first inbound webhook for a new, live SID with the true numbers
  receives that admission's relay token.
- **Replay.** Signatures do **not** protect against replay either: an HMAC binds a request's URL and body, not its
  freshness, so a captured signed request verifies again. Replay safety comes from the state machine (terminal
  states are final, inbound SIDs are admitted once, Connect completions are processed once per generation, relay
  tokens are single-use), in both modes.
- **Webhook parameters are unauthenticated** except what the REST record confirms (account, direction, from, to,
  status). Other fields (e.g. `Digits`, `AnsweredBy`) are taken as sent.
- **Availability:** every first webhook of a leg waits for a Twilio REST round trip, and if the API is unreachable
  the plugin refuses the request (fails closed), so a Twilio API outage stops calls that signatures would let through.
- The REST check costs one API request per leg plus one per terminal or conference-end event and one per inbound
  admission; Twilio API rate limits apply. Any charge for these lookups was not checked.
- **Downgrade:** a configured Auth Token that cannot be read stops the service ("configured but cannot be read");
  it never falls back to path-secret mode. `ingress_auth: signature` refuses to start without the token.
- **Media Streams (voice path, R1 delta 2 wording).** The same bearer-secret limits apply to the media and digits
  routes; none of these is a path-secret bypass of its own:
  - a stolen media URL (path secret plus an unused current-generation token) can win the first-upgrade race, and
    the real stream is then refused (one socket per call);
  - a correct `start` CallSid is correlation, not proof of who is speaking;
  - a leaked digits nonce can be consumed early by whoever holds it;
  - an accepted HTTP response that contains an unused current media token discloses it to the requester;
  - an invalid digits nonce authenticates nothing further: its response can contain the current stream TwiML, just
    as `/answer` can.
  *Fixed (N2):* a valid nonce arriving after the owner was rung or took over, or while the call is ending, plays
  nothing, opens no stream and changes no generation (both modes).

**Notification 15003 is ours.** Twilio raises 15003 ("Call Progress: Warning Response to Callback URL") when a callback
URL answers late or with an error. Our status handler awaited the model-written summary (up to 25 s), and at stop it
was cancelled, so Twilio got a timeout. Now `finalize` updates the state, tells the relay to end, and returns; the
summary (bounded by `summary_timeout_s`, default 10 s), the outbox entry, closing the driver and the session cleanup
run in a background wrap-up. A stop gives wrap-ups 2 s and then records the plain summary. The status callback now
answers in 2-7 ms (replay below).

**Fixes:**
- **A reply to the live-person question always gets an answer.** Within `confirm_reply_window_s` (15 s) of the
  question, an unclear reply gets a re-ask ("Sorry, I didn't catch that. Am I speaking with a live person?"). A second
  unclear reply hands over to Hermes with a note that it is not certain they are a person. Unprompted speech
  (recordings) keeps the 45 s cooldown.
- **Classification never keeps a person waiting.** The detector gets `reply_budget_s` (2.5 s, at most 3). After that,
  Hermes speaks (the question or the re-ask) and a late verdict still applies (human, IVR, voicemail, hold).
  - Detector questions and the summary run on their own worker (`ask_executor`), and the tracker update for our own
    question is queued, not awaited, so a slow detector cannot hold up the next utterance. Not awaiting it was a
    second bug, found by the slow-detector replay.
  - `AcpDriver.ask` streams into its own slot in its own ACP session, so a question can overlap a spoken turn.
- **Fillers.** While a spoken Hermes turn has produced no text, a fixed line ("One moment.", …) is sent every
  `reply_budget_s`, at most three times.
- **Owner self-test.** An outbound call whose destination is `owner_number` is the owner testing the line: no
  live-person question; the first words go to Hermes with a note that this is the owner.
- **Hints.** ConversationRelay gets `hints` with the owner's name and the capitalised words of the task title (letters
  only, at most 8), so "Can" is expected and not heard as "Ken".
- **Connect action after hangup.** A `<Connect action>` whose `CallStatus` is ended (completed, busy, failed,
  no-answer, canceled) gets `<Hangup/>`: no recovery, no token, no debit. It is not cached, so a forged "completed" in
  fallback mode cannot end the real call: Twilio's own completion is still processed.

## 16. Round 7, part 2: callbacks over a forwarded line

**Design (coordinator decision).** Outbound calls show the owner's Fi line as caller ID (a Twilio verified caller
ID). A business that calls back reaches the Fi line, which forwards every call to the plugin's Twilio number
(`line_number`), and Hermes answers there.

**What L1 does with a forwarded inbound call.**
- Admission and H2 are unchanged: `To` must be `line_number`, each CallSid is admitted once, and the REST record is
  checked in fallback mode.
- `From` is the original caller and is matched to an open task by number and time window, exactly as before
  (`match_callback`: a unique task whose destination equals the caller, status calling / awaiting callback /
  failed, within `callback_window_hours`).
- `ForwardedFrom` (when the carrier passes it) and `CallerName` (CNAM, when present) are recorded: masked, and the
  name sanitised to 40 characters. They never grant anything.
  - The caller name goes into Hermes's briefing as an unverified note.
  - If `From` is one of our own numbers (the forwarding line, caller ID, line or owner number), the forwarding hid
    the caller: no task match, and Hermes asks who is calling.
- **Unknown callers** get the greeting with the AI disclosure ("…This is Hermes, an AI assistant. How can I help?")
  and the instruction to take a short message and finish with it as the summary, which reaches the owner.
  - With `inbound_ring_owner` (default true) and an `owner_number`, the call gets one single-use
    `bridge_owner_callback` grant. If the caller needs the owner, Hermes's `bring_owner` rings only the owner's own
    phone (destination gate, quiet hours), and the owner presses 1 on the whisper to be connected.
  - Any other key is a decline (`owner_declined`): the owner leg ends and Hermes carries on at once. No answer behaves
    the same.
  - One ring per call. With `inbound_ring_owner: false` the ring is refused at the gate and nobody is dialled.
- A caller who hangs up early ends the call as `business_hangup`; nobody is rung, and the SID cannot be admitted
  again.

**User-side setting.** On the forwarding line (Fi), forward all incoming calls to the plugin's Twilio number
(`line_number`). Verify the Fi number as a caller ID in Twilio and use it as `from_number`, so businesses see and
call back the Fi line. Set `forwarding_number` to the Fi number so forwarded calls are recognised in the log. Calls
to Fi then ring Hermes, not the phone, while forwarding is on. Callbacks are matched only when the forwarding
passes the original caller ID through; otherwise Hermes answers them as unknown callers. The Fi steps themselves are
written by another lane.

## 19. Round 10: R1 delta 5 N7, an owner stop while the agent starts

**Finding.** Commands run one at a time, so an owner Hang up (or cancel) submitted while the call's agent was
starting waited behind the whole approve, startup and dial operation: the call was dialled, then hung up. The
reviewer's `probe_cancel.py` got one provider call, and its cancel got "no task awaiting approval".

**Fix (`engine/service.py`, `store/db.py`).**
- **Stop recorded outside the queue.** `_dial` puts a call in `_starting` from session creation until its final
  pre-dispatch check. A stop (`hang_up` for that call; `cancel`, or `deny` from an owner source, for its task) is
  recorded as intent in `submit` under `_stop_lock` before the command is queued.
- **Final check under the same lock.** `_claim_dispatch` runs right before `gate.authorize` and `place_call`, with
  no await before the dial. It takes the call out of `_starting` and reads the in-process intent, and also any
  unfinished stop command in the store (`Store.pending_stop`), so a stop submitted from another process wins too.
- **Honoured stop.** The provisional session ends (`ended`, `hung_up_by_owner` for a hang-up, `canceled` for a
  cancel or deny); the task is `canceled`, outcome "stopped before dialling"; a `stopped_before_dialling` event is
  logged and grants are dropped. Nothing is dialled.
- **The owner hears it at once.** While the call is still in `_starting`, `submit` promises the stop and answers
  "Stopped before dialling: … nothing was dialled." immediately (`/line hangup`, `/line deny`, Desktop cancel), and
  the queued stop command later finishes with the same result. Past the final check the call is being dispatched:
  nothing is promised, and a hang-up ends the call after the dial, as before.
- **Cancel after dispatch.** An explicit owner cancel of a task whose call is already live now hangs that call up
  (it used to answer "no task awaiting approval").

**Tests** (`tests/l1/test_r10_n7.py`, through the real `/line` routing in `hermes_glue.py` and the service command
queue; startup paused as in `probe_cancel.py`):
- `test_N7_line_hangup_during_startup_dials_nothing_and_says_so_at_once` (answer in under 1 s, zero provider calls,
  session, agent and tokens cleaned up).
- `test_N7_line_deny_during_startup_is_a_cancel_before_dialling`, `test_N7_desktop_cancel_through_the_queue_during_startup`.
- `test_N7_stop_from_another_process_is_read_from_the_store`, `test_N7_a_tool_cannot_deny_on_the_owners_behalf`.

## 20. Round 11: R1 delta 6 N8, rejected commands leave no stop

**Finding (Low).** Round 10 recorded the stop intent before the command passed validation. A `call-agent` hang-up
(which the executor refuses: "not an in-call action") and an owner hang-up with a stale `expected_revision` (which
the queue refuses with `StaleRevision`) still stopped a starting call.

**Fix.**
- `CallService.stop_acceptable(action, source)` is the executor's own rule for a stop: never from `call-agent`, and
  `deny` only from an owner source.
- `submit` records the intent only for an acceptable stop, and only after `enqueue_command` accepted the row: a
  new idempotency key, and the revision checked. Enqueue and intent run under the same `_stop_lock` as the
  dispatch claim, so the claim sees neither or both, and the immediate "stopped before dialling" promise stays
  exact.
- `Store.pending_stop` (stops from another process) applies the same rule and skips a row whose
  `expected_revision` is stale against the call's current control revision, as `_stale_command` would.

## 26. Round 17: live-leg owner bridge (the hook L6 round 9 names)

Opt-in setting `owner_live_bridge` (default `false`). When it is off, nothing changes: an approval keyed on the owner
line is dialled after the owner hangs up, and the owner is rung back. L6's ring-back harness
(`tests/l6/test_ringback.py`) asserts exactly that flow, so the default stays off; the harness turns it on with
`owner_live_bridge=True`.

**When the bridge is used.** All of these must hold (`CallService.live_bridge_possible`):
- the setting is on, the task is an owner-mode task (`bring_owner`), and `owner_number` is set;
- the parent is an inbound call, PIN-verified, not terminal, on ConversationRelay, and its caller ID is
  `owner_number`;
- the parent has no child yet.

The read-back then says "…about X now, and connect you on this call when a person answers". The keypad
confirmation (four or seven digits, round 16) is unchanged.

**Approval.**
- `voice_approve(..., live=True)` records the ticket (`owner_voice_approved` with `live_bridge`) and queues the
  `owner-voice` approve at once, with the parent's call id.
- The ticket is valid for `LIVE_DIAL_WINDOW_S` (30 s). After that it is refused (`owner_bridge_ticket_expired`), the
  owner hears so, nothing is dialled, and the task waits for chat approval.
- If the owner hung up before the approve ran, it is a normal approve. It dials once the line is free and rings the
  owner back.

**Busy-line control.** `_approve` keeps refusing while any call is live, with one exception: the ticket's parent is
the only live call and the only session, and still passes `live_bridge_possible`. The parent's in-call
`owner_new_task` refuses a second request while a child exists ("one call at a time"). These stay blocked: other
approvals from chat, owner-voice approves without a matching ticket (including forged ones that carry a parent id),
and inbound calls (busy). The child goes through `_dial` unchanged: destination gate, quiet hours, the consumed dial
token, the restricted-profile scope check before the dial, and N7 stops.

**Link and events.** `_dial` links the child to the parent as soon as its session exists:
- `session.parent` and `session.child` hold the pair, and `children_started` counts the parent's children.
- The parent logs `child_call_linked` (`child_call_id`); the child logs `parent_call_linked` (`parent_call_id`).

**On a confirmed person** (round 16: an L2 HUMAN verdict or a clear yes), the owner-mode child calls
`bridge_live_owner` instead of `ring_owner`.
- **Gate:** the task's `bridge_owner` grant goes through `gate.authorize` (owner number, consent consumed) exactly as
  for a ring. If it is refused, the event is `owner_ring_rejected`, there is no bridge, and the existing
  `owner_unavailable` path runs.
- **Child:** state `OWNER_CONNECTED` (new edge from `HUMAN_DETECTED`), conference `hl-<child id>`, and `owner_sid`
  set to the parent's inbound CallSid. The existing hang-up and status teardown therefore also end the owner's leg.
- **Parent:** Hermes is cut off, then the fixed line "Someone answered about X. Connecting you now.", state
  `OWNER_CONNECTED` (new edge from `AGENT_TALKING`), and the same conference.
- **Joining:** after the spoken line, both legs join through the existing hand-off: relay `end` with handoffData,
  then the Connect action returns the conference; with no relay socket the leg is redirected to `conference/join`.
  Both legs' conference TwiML reports to the child's conference status URL (`conference_twiml`,
  `conference_status_id`).
- **Events:** `owner_bridged` on both calls, with `owner_dialled: false` on the child. No owner call is created.

**Endings** (`linked_call_ended`, called from `finalize`):
- **Bridged, either side ends** (conference end, business hang-up, owner hang-up, max duration, error): the other
  call is hung up too. The parent ends `owner_finished` and the task is done.
- **Child ends before the bridge** (no answer, busy, voicemail, cancel, failure): `child_call_ended`. The owner
  hears "An update on the call about X: nobody answered / the line was busy / you cancelled it / it ended (…)", and
  Hermes gets a note. The parent call stays up and may ask for another call.
- **Owner hangs up first:** `parent_call_ended` with `next: ring_back`. The child carries on; on a person it rings
  the owner with the normal whisper and press 1 (the ring-back fallback).
- **Cancel:** star on the parent's keypad before the bridge (`child_cancel_keyed`) stops a child that is still
  starting (N7 intent) or hangs it up. `/line cancel` in chat works as before and is reported on the parent.
- **Dial refused before the child session exists** (for example by the destination gate): the owner hears "it
  could not be placed (…)".

**Limits:**
- Untested on Twilio. Twilio may honour only the first participant's conference `statusCallback`, so both legs
  report to the child's URL, and each call's end also ends the other.
- If moving a leg fails, both calls end; there is no ring-back after a failed move.
- The business leg waits silently in the conference for the moment the owner's line takes to be spoken.

### B9: the phase list (field contract for L3)

`GET` call data (`desktop_api.call_view`, the snapshot the pane reads) has:

```
"phases": [{"phase": "<name>", "since": "<ISO 8601 UTC, ms, +00:00>"}, ...]   // oldest first
```

This is exactly L3 round 7's shape. Names:

| phase | opened by |
|---|---|
| `dialing` | state `dialing` |
| `menu` | state `ivr` (a phone menu) |
| `assistant` | state `ivr` for an automated assistant (the "automated assistant" transition, or any IVR state after a bot label) |
| `hold` | state `on_hold` |
| `person` | states `human_detected` and `agent_talking` (a person confirmed; on inbound calls, the caller) |
| `owner_ringing` | state `ringing_owner` |
| `bridged` | state `owner_connected` |
| `fallback` | state `agent_talking` after the owner did not take the call (the fallback question, or Hermes continuing) |
| `ended` | states `ended` and `failed` |

**Rules:**
- **Who writes it:** the store writes the list in the same transaction as every stored state change
  (`update_call(state=…, phase=…)`, with `CallState` → `STATE_PHASE`; the engine names `assistant` and `fallback`).
- **No repeats:** a repeat of the current phase is not appended, so consecutive entries always differ.
- **Before the dial:** `awaiting_approval` opens no phase. A call that was never dialled has `[]` or only `ended`.
- **Returning phases:** after the owner's ring ends without an answer, a call that was waiting goes back to
  `menu`/`assistant`/`hold`.
- **Ends:** a phase ends where the next one begins. The current phase of a live call is open. `ended` is the last
  entry of a finished call.
- **Migration:** older databases get the column (`phases TEXT NOT NULL DEFAULT '[]'`) on open, and their calls read
  as `[]`. L3 falls back to deriving the phases from the transcript.

**L3 follow-up (outside L1's paths):** `plugin/desktop/plugin.js` `PHASE_ALIASES` on main does not yet know
`assistant`, `owner_ringing`, `bridged` or `fallback`, so it skips those entries. Suggested mapping:
`assistant`→menu, `owner_ringing`/`bridged`/`fallback`→person.

## 53. Round 41: R1b delta 37 B2 (blocking). Renewal never counts speech as silence

**The finding:**
- `unheld_marks` held the START stamp of outside-hold speech, and `_new_hold_segment` compared against `now`;
- so a 110 s recording (continuous partials from 200 to 309, final at 310) earned a new segment, and two such
  recordings exhausted the cap of 12 before the real agent;
- a previous utterance's start was also taken as its end.

**The fix:**
- **End stamp:** a final now carries `ended_at`, its arrival (its last frame). `offer` sets it as the internal
  `_ended_at`, which is stripped from relay frames like `_started_at`. `SpokenUtterance.ended_at` marks the END of
  outside-hold speech in `unheld_marks`. The immutable `started_at` still decides confirmation only.
- **The renewal rule** (`_new_hold_segment`): a new segment needs a qualifying 120 s of hold or no business speech
  entirely before the current utterance began:
  `current start - max(last question send, end of the last outside-hold speech before it) >= 120`.
- **Continuous on_hold:** speech heard while on hold, or labelled `hold_message`/`hold_music`, never marks. So
  "continuous on_hold for 120 s before the current start" is part of the same rule.
- **Which start:** the current start is the utterance's `started_at`. For the stall question, it is the pending
  partial's start; without either, `now`.
- **No false intervals:** the same utterance is used at the send guard and at the segment reset, so processing time
  never creates an interval.
- **Unchanged:** 20 s spacing, 4 per segment and the cap of 12.
